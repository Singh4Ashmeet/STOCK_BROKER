# DevOps and Deployment

Constraint: **free to build and run**. Local-first; a public demo is optional and uses free tiers.

## 1. Repository and environments

- Monorepo (this folder). Single `proto/` source of truth.
- Environments: `dev` (laptop), `ci` (GitHub Actions), `demo` (optional free VM). No production beyond the demo.

## 2. Docker Compose layout

Use compose **profiles** so a laptop only runs what it needs:

| Profile | Services |
|---|---|
| `core` | Postgres, Redis |
| `analytics` | ClickHouse |
| `obs` | Prometheus, Grafana (and Alertmanager optionally) |
| `bus` (optional, off by default) | Redpanda or NATS JetStream |
| `app` | feed, api, research, web (containers; for demo and CI. In dev run these natively) |

Examples:
```
docker compose --profile core up -d                       # minimum for Java development
docker compose --profile core --profile obs up -d         # plus dashboards
docker compose --profile core --profile analytics --profile obs --profile app up -d   # full stack
```

Compose conventions: named volumes for data; healthchecks on every service; `depends_on: condition: service_healthy`; resource limits for the demo VM; `.env` for ports and passwords (generated by a bootstrap script); internal network with only the proxy/web/api ports published.

## 3. Dockerfiles (multi-stage, small, non-root)

| Service | Build | Runtime |
|---|---|---|
| feed | `rust:slim` + `cargo build --release` (cargo-chef for caching) | `debian:stable-slim` or `gcr.io/distroless/cc`; non-root; `HEALTHCHECK` on the HTTP health port |
| api | Gradle/Maven build on a JDK 21 image | JRE 21 (Temurin) slim; non-root; container-aware JVM flags |
| research | `python:3.12-slim` build stage builds the PyO3 wheel with maturin | slim runtime with wheel installed; non-root |
| web | Node LTS build; Next.js `output: "standalone"` | Node slim, standalone server, non-root |

Pin base image tags (digests for releases). Generate an SBOM and scan with Trivy in CI.

## 4. CI/CD (GitHub Actions)

Workflows:
| Workflow | Triggers | Jobs |
|---|---|---|
| `proto.yml` | PR touching `proto/` | `buf lint`, `buf format -d --exit-code`, `buf build`, `buf breaking` against base, Python compile check |
| `rust.yml` | PR touching `rust/` or `proto/` | detect → fmt, clippy -D warnings, tests, property tests, cargo-audit/deny, criterion smoke, build wheel artifact |
| `java.yml` | PR touching `java/` or `proto/` | detect → build, unit, Testcontainers integration, dependency check |
| `python.yml` | PR touching `python/` | detect → ruff, mypy --strict, pytest, Hypothesis, pip-audit, parity test |
| `web.yml` | PR touching `frontend/` | detect → lint, typecheck, Vitest, build, bundle-size check |
| `e2e.yml` | nightly + manual | compose up with replay fixtures, Playwright |
| `bench.yml` | manual + weekly | benchmarks on a stable runner; upload results (CI noise is high; treat CI benchmarks as regression signals only, publish numbers from a controlled machine) |
| `security.yml` | PR + nightly | gitleaks (via Docker), Trivy fs + config scanners (HIGH/CRITICAL), .trivyignore for documented exceptions |
| `release.yml` | tag `v*` | build images, SBOM, changelog, attach artifacts |

**Detect-step gating**: Each language workflow starts with a `detect` job that checks if the project directory exists (e.g., `test -d rust && test -f rust/Cargo.toml`). The output (`exists=true/false`) gates subsequent jobs via `if: needs.detect.outputs.exists == 'true'`. This allows workflows to pass (no-op) before the corresponding project exists.

**SHA pinning policy**: All third-party GitHub Actions are pinned by full commit SHA with a `# vX.Y.Z` comment. If network access is unavailable during authoring, a `# TODO(pin-sha)` comment is added and listed in the PR.

**Security.yml design**: Uses `gitleaks/gitleaks-action` (not paid license) and `aquasecurity/trivy-action` for filesystem + config scanners. Fails on HIGH/CRITICAL. Exceptions documented in `.trivyignore` with header comments justifying each.

Practices: cache Cargo/Gradle/pip/npm; matrix only where useful; required status checks on `main`; path filters to keep CI fast; reusable workflows for shared steps.

## 5. Versioning and releases

- Semantic versioning per repo release (`v0.x` until stable). Changelog generated from Conventional Commits.
- Proto packages versioned (`v1`); the Rust wheel version is the workspace version and is recorded in each backtest.

## 6. Configuration

| Layer | Mechanism |
|---|---|
| Rust | TOML file + env overrides (`SB_FEED_...`) |
| Java | `application.yml` + env (`SB_API_...`), Spring profiles `dev`/`demo` |
| Python | env + pydantic settings |
| Web | `NEXT_PUBLIC_*` only for non-secrets; server secrets via env |

A `scripts/bootstrap` step generates local dev secrets (JWT keypair, DB passwords) into `.env`, which is git-ignored.

## 7. Free-hosting options for a public demo (**VERIFY** current terms and availability)

| Option | Use | Notes |
|---|---|---|
| Local machine + screen recording | Safest | Costs nothing; README embeds a video; best for latency numbers |
| Oracle Cloud Always Free VM (Arm or AMD) | Run compose for feed + api + web + DBs | Generous free tier historically; capacity and terms vary; verify region availability and that idle-reclamation policies suit you |
| Free tiers of other clouds | Short trials | Typically time-limited credits, not indefinite |
| Cloudflare Pages / Vercel (free) | Static or serverless Next.js pages | Not suitable for long-lived WebSockets; point the WS to the VM |
| Cloudflare Tunnel | Expose a home machine securely | Free; keep a read-only demo mode |

**Demo mode:** a public demo should be read-only for the live market views plus a rate-limited paper-trading sandbox (or invite-only), with aggressive per-IP limits and quotas on backtests.

## 8. Data volume and retention

- Estimate event-log volume by measuring in Phase 2 (messages per second per symbol times bytes per message after zstd) and project daily growth for 5 symbols.
- Retention defaults: raw logs 7 days on the demo VM; ClickHouse TTLs as in `05-DATA-MODEL.md`; keep a few curated "golden days" (small) for tests and demos.
- Disk alerts at 85 percent; the feed pauses log writing (not the live stream) below a configured free-space threshold.

## 9. Backups and recovery

- Postgres: nightly `pg_dump` (encrypted) to off-host storage (free object storage tier or a second machine); weekly restore test script.
- Configs and dashboards live in git. Event logs are reproducible from the exchange only for recent history; accept that raw logs are not backed up beyond curated fixtures.
- Recovery runbook in `docs/runbooks/` (to be written in Phase 8): feed restart, DB restore, key rotation, demo redeploy.

## 10. Operations runbook outline (write during Phase 8)

Start/stop, health checks, reading dashboards, common alarms and responses (feed disconnected, book invalid, disk low, ledger diff), rotating secrets, upgrading, restoring.

## 11. Cost guardrails

No paid dependency may be introduced without an ADR. Prefer open-source, self-hosted components. Verify that free-tier usage cannot silently convert to paid billing (set budget alerts or use providers without auto-billing).
